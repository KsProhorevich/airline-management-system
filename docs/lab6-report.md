# Лабораторная работа №6. Blazor, тесты, Docker и CI

## Клиент

Проект `AirlineClient`, модель Blazor Web App с интерактивностью Server (`AddInteractiveServerRenderMode`). Выбран Server, а не WebAssembly: запросы к API делает сервер клиента. В Docker базовый адрес — `http://api:8080`, имя службы compose, не `localhost` внутри контейнера. Локально `Api:BaseUrl` равен `http://localhost:5080`. Клиент слушает `http://localhost:5081`.

Клиент не открывает SQLite и не повторяет правила мест. Ошибки API показываются из `detail` или `errors` ответа `ProblemDetails`.

Токен хранится в `ProtectedSessionStorage` на время сеанса схемы и в scoped-состоянии контура. Это не `localStorage`. Пароль после входа очищается из модели формы и на сервер API уходит только в теле login/register. Ключ подписи JWT клиенту не известен. Скрытие кнопки не заменяет авторизацию API.

Страницы на русском: вход, регистрация пассажира, список и карточка рейсов, создание и изменение для диспетчера, фильтр, сортировка и страницы, самолёты, брони пассажира и диспетчера, создание и отмена брони, список пассажиров для диспетчера. Используются `EditForm`, `DataAnnotationsValidator`, `@bind`, `EventCallback`, `@inject`, жизненный цикл и `NavigationManager`.

## Тесты

Один прогон `dotnet test AirlineApi.sln` дал 40 пройденных случаев. Категории разные, интеграционные не считаются модульными.

| Категория | Количество | Где |
|---|---|---|
| Модульные, сервис бронирования, Moq | 6 | `BookingServiceTests` |
| Модульные, правила формы брони | 2 | `BookingFormRulesTests` |
| Интеграционные, `WebApplicationFactory` | 29 | прежние 26 и 3 новых маршрута |
| Интеграционные, ADO.NET и EF Core на временном файле | 3 | `AdoNetAndEfTests` |

Модульных всего 8, из них 6 проверяют бизнес-логику сервиса: хватает мест, мест не хватает, повторная бронь, владелец из токена, отмена возвращает места, статус рейса не позволяет бронь. Временные базы SQLite не используют `App_Data/airline.db`.

## Docker

`AirlineApi/Dockerfile` и `AirlineClient/Dockerfile` — многостадийные. `docker-compose.yml` поднимает `api` и `client`. Том `airline-data` смонтирован в `/data`, строка подключения `Data Source=/data/airline.db`. Точка входа API от root создаёт каталог, делает `chown 1654` и при наличии `setpriv` запускает процесс от этого пользователя. Секреты в образ не копируются: `Jwt__SigningKey`, `Admin__Email` и `Admin__Password` приходят из окружения. Пример имён переменных — `.env.example`, без рабочего ключа.

Проверка сборки образов выполняется отдельно и фиксируется в `docs/labs-completion-plan.md` только по фактическому результату команды.

Фактически: `docker compose build` завершился успешно, `docker compose up -d` дождался healthy у API. Оба `/health` ответили `ok`, в контейнере было 5 учебных рейсов. Контейнеры остановлены через `docker compose down`. Том данных сохранён. Публикация в GHCR не запускалась.

## GitHub Actions

`.github/workflows/ci.yml` на push и pull request восстанавливает, собирает и тестирует `AirlineApi.sln`, затем публикует каталоги сборки как артефакт. Образы в GHCR публикуются только при push в `main` или `master`, через `GITHUB_TOKEN` и `packages: write`. Pull request образы не публикует и секреты приложения не требует.

Публикация в реестр этим сеансом не выполнялась. Workflow в репозитории есть, успешной публикации нет.
