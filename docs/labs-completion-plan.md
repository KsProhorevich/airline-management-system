# План завершения лабораторных работ 4, 5 и 6

Дата осмотра: 17 октября 2026. Основа — уже собранный `AirlineApi` лабораторной №5. Каталог `lab4` по-прежнему содержит загрузчик файлов без базы авиакомпании. Текущая схема SQLite не заменяется чужим проектом.

## Что уже есть

- `AirlineApi.sln`: API `net8.0`, Minimal APIs, EF Core SQLite 8.0.32, JWT, роли `Dispatcher` и `Passenger`.
- Сущности `User`, `Flight`, `Booking`. Пассажир — это `User` с ролью `Passenger`.
- Репозитории, `IUnitOfWork`, сервисы, DTO, `ProblemDetails`, пагинация, фильтры, сортировка, Swagger.
- Миграция `20261017203737_InitialCreate`. Её не переписывать.
- 26 интеграционных тестов на `WebApplicationFactory` и временном SQLite.
- Секреты JWT в репозиторий не входят.

## Чего не хватает

| Работа | Пробел | Намерение |
|---|---|---|
| 4 | Нет воздушного судна и связи рейс–судно | Сущность `Aircraft`, внешний ключ, новая миграция |
| 4 | Нет явного ADO.NET | `AdoNetDemoService`: параметр, `DbDataReader`, commit и rollback. Чтение доступно диспетчеру, произвольный SQL клиенту не отдаётся |
| 4 | `ExecuteUpdate` / `ExecuteDelete` и `ChangeTracker` не показаны | Отдельная демонстрация в тесте, не в правилах бронирования |
| 4 | Отдельная сущность пассажира | Не добавлять: `User` уже является пассажиром. Искусственную связь один-к-одному не вводить |
| 5 | Контракт создания рейса | `aircraftId` необязателен: старые клиенты и тесты продолжают работать, подставляется резервное судно |
| 6 | Нет Blazor, Docker и CI | Клиент Interactive Server, `docker-compose.yml`, workflow GitHub Actions |
| 6 | Нет модульных тестов сервиса с подменой зависимостей | xUnit + Moq для `BookingService`, интеграционные тесты сохраняются |

## Риски совместимости

- Обязательный `AircraftId` у рейса ломает уже созданные строки. Миграция сначала создаёт резервное судно и заполняет столбец.
- Новые поля в `FlightResponse` добавляются, старые не удаляются.
- Blazor Server ходит в API с сервера контейнера по имени службы `api`, а не через `localhost` браузера.
- Публикация образов в GHCR проверяется только если есть Docker и доступ к реестру. Иначе workflow остаётся в репозитории и помечается как не прогнанный.

## Итог реализации

Сделано в коде:

- `Aircraft`, связь с рейсом, миграция `AddAircraft` без переписывания `InitialCreate`.
- `AdoNetDemoService`, чтение для диспетчера, тесты параметра и отката.
- `EfCoreFeatureDemo` только в тесте.
- Эндпоинты судов и списка пассажиров, поля самолёта в ответе рейса.
- `AirlineClient` Blazor Server.
- Модульные тесты Moq и правила формы. Общий прогон: 40 пройдено.
- `Dockerfile` API и клиента, `docker-compose.yml`, `.github/workflows/ci.yml`.

Фактически выполнено:

- `dotnet build AirlineApi.sln` — успешно, 0 ошибок.
- `dotnet test AirlineApi.sln` — 40 пройдено, 0 не пройдено.
- `dotnet ef migrations list` — обе миграции были Pending на пустом каталоге.
- `dotnet ef database update` — создан новый `AirlineApi/App_Data/airline.db`, обе миграции применены. Старую базу удалять не пришлось: файла не было.
- `dotnet ef migrations remove` — не запускался.

Не проверено до отдельной отметки ниже: сборка Docker, вход через браузер, публикация GHCR.

Проверено после реализации:

- `docker compose build` собрал образы `lab5-api` и `lab5-client`.
- `docker compose up -d` поднял API до состояния healthy. `GET http://localhost:5080/health` и `GET http://localhost:5081/health` вернули `status: ok`. Список рейсов контейнера содержал 5 рейсов, первый `SU050` на `RA-73001`. Контейнеры затем остановлены командой `docker compose down`. Том `lab5_airline-data` оставлен.

Локальный файл базы после этой проверки удалён, потому что в нём остался хеш временного пароля. Публикация в GHCR не выполнялась.
